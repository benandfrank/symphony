# Linear GraphQL API Reference

LLM-friendly reference for the Linear API as used by Symphony's Linear adapter.

**Endpoint:** `https://api.linear.app/graphql`  
**Protocol:** GraphQL over HTTP POST  
**Auth:** `Authorization: <api_token>` header (personal API key or OAuth token)  
**Content-Type:** `application/json`  
**Rate limits:** Varies by plan; 429 response when exceeded

---

## Authentication

```
Authorization: lin_api_XXXXX
Content-Type: application/json
```

Personal API keys are generated in Linear Settings → API → Personal API Keys.

---

## Request Shape

```json
{
  "query": "query { ... }",
  "variables": { "key": "value" },
  "operationName": "OptionalOperationName"
}
```

Response on success (HTTP 200):

```json
{
  "data": { ... }
}
```

Response on GraphQL error (still HTTP 200):

```json
{
  "errors": [{ "message": "...", "locations": [...], "extensions": {...} }]
}
```

## Key Issue Fields

```json
{
  "id": "uuid",
  "identifier": "MT-42",
  "title": "Fix bug",
  "description": "markdown description",
  "priority": 2,
  "state": { "name": "Todo" },
  "branchName": "feature/mt-42-fix-bug",
  "url": "https://linear.app/team/issue/MT-42",
  "assignee": { "id": "uuid" },
  "labels": { "nodes": [{ "name": "bug" }] },
  "inverseRelations": {
    "nodes": [
      {
        "type": "blocks",
        "issue": { "id": "uuid", "identifier": "MT-10", "state": { "name": "In Progress" } }
      }
    ]
  },
  "createdAt": "2024-01-01T00:00:00.000Z",
  "updatedAt": "2024-01-02T00:00:00.000Z"
}
```

Key differences from ClickUp:
- `assignee` is a single object, not an array.
- `assignee.id` is a string UUID (ClickUp uses integer IDs).
- `priority` is an integer `0`–`4` (0 = no priority, 1 = urgent, 4 = low).
- `branchName` is a native field; ClickUp has no equivalent.
- Blockers are expressed as `inverseRelations` where `type == "blocks"`.
- Timestamps are ISO 8601 strings; ClickUp uses Unix millisecond strings.

## Pagination

Linear uses cursor-based pagination. Each page response includes:

```json
{
  "pageInfo": {
    "hasNextPage": true,
    "endCursor": "cursor-string"
  }
}
```

Pass `after: <endCursor>` in the next query's variables to get the next page.
Continue until `hasNextPage` is `false`.

---

## Viewer Query (resolve "me" assignee)

```graphql
query SymphonyLinearViewer {
  viewer {
    id
  }
}
```

Used to resolve `assignee: "me"` to the authenticated user's Linear ID.

---

## Error Responses

- **HTTP 200 with `errors` array** — GraphQL error (invalid query, permissions, etc.)
- **HTTP 401** — invalid or expired API token
- **HTTP 429** — rate limit exceeded; `Retry-After` header contains seconds to wait
- **HTTP 500** — server error

**Rate limit handling in Symphony:** `Linear.Client.graphql/3` automatically retries 429
responses using `Tracker.Retry`. It honors the `Retry-After` header when present and parseable
(positive integer seconds). Falls back to bounded exponential backoff (default: 1 s base, 30 s
cap, 3 max attempts) when the header is absent or invalid. Non-429 responses and transport errors
are never retried.

---

## Known Gotchas

- GraphQL errors return HTTP 200, not 4xx. Always check for an `errors` key in the response body.
- `priority: 0` means "no priority" (not urgent). Linear uses 1–4 for actual priorities.
- `inverseRelations` must be queried with a `first:` limit; there is no implicit page limit.
- The `branchName` field is auto-generated by Linear and may differ from the actual Git branch.
- `assignee` can be `null` if the issue is unassigned.
